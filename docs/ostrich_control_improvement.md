## Current state 
The "motor" isn't modeled as a torque-limited device at all — it's modeled as an ideal velocity source with finite stiffness (k_p) but infinite authority. Whatever torque is needed to null the velocity error each step, it applies. k_p only shapes how aggressively it chases the setpoint (and, as we discussed, sets an effective first-order time constant I/k_p) — it's not a proxy for torque capacity, and nothing in the current code path would stop λ from reaching an arbitrarily large value under a big enough velocity error.

## Ostrich already has a hard cap on what torque reaches the ground
The friction cone (mu·N·r, ~107 Nm/wheel per the demo comment at mu=0.8). Today, whenever the velocity error is large enough for the unbounded P-law to demand more than that, the friction constraint is already the thing doing the clamping — so in that regime, adding a motor torque cap changes nothing, because physics was already saturating first. The cap only starts mattering, and only then closes sim-to-real gap, when the real motor's stall/peak torque is below the friction budget — plausible for a geared skid-steer drive — because right now the sim would happily supply more torque than the real motor could ever deliver, right up to that friction ceiling.

Practically: fit saturation_effort from the bag and compare it to ~107 Nm. If it's meaningfully lower, the cap is worth doing — it directly attacks the exact quantity ostrich_vel_cmd.py is studying (achieved-vs-commanded yaw), since currently the sim may be over-crediting the robot with turning authority it doesn't really have. If it's comparable or higher, the friction model is already the binding constraint and other gaps (k_p/bandwidth mismatch, contact/terrain fidelity) are probably higher-leverage than the torque cap.
